## 1. Freeze the release and prepare recovery

After explicit delivery approval, coordinate with the independently managed main
worktree. Recheck remote main: the integration base was `cc0b54b`; newer changes
need a scoped compatibility review before any merge. Merge integration into main
only in an authorized, clean checkout; record its exact merge SHA and license diff.
Do not rewrite feature history or remove worktrees. Tag/release come last.

Schedule a short maintenance window outside collection/session activity where
possible. Freeze **all** producers: financial preparations/confirmations, browser
approval writes, ingestion, scheduled dispatch and already-running collectors.
`FINANCIAL_WRITES_ENABLED=false` removes financial write permission but does not
stop quotation ingestion. Record prior settings privately and drain in-flight work.
Let outstanding proposals expire; do not approve or replay one during cutover.
Changing this flag is a deployment/configuration action needing delivery authority.

Record current Worker version/bindings and the database migration list. Confirm
0001–0007 are already applied. **Do not replay 0007**: its empty-journal guard is
incompatible with a populated journal. Unexpected missing/reordered migrations
are a stop condition, not a reason to reset tables or rewrite history.

With existing, verified configurations, the future operator commands are:

```sh
node node_modules/wrangler/bin/wrangler.js deployments list --config '<FINANCIAL_CONFIG>'
node node_modules/wrangler/bin/wrangler.js d1 migrations list '<EXISTING_DB>' --remote --config '<DB_CONFIG>'
node node_modules/wrangler/bin/wrangler.js d1 info '<EXISTING_DB>' --config '<DB_CONFIG>'
node node_modules/wrangler/bin/wrangler.js d1 time-travel info '<EXISTING_DB>' --config '<DB_CONFIG>'
node node_modules/wrangler/bin/wrangler.js d1 export '<EXISTING_DB>' --remote --config '<DB_CONFIG>' --output '<PRIVATE_EXPORT.sql>'
```

These are templates, **not commands executed in this task**. Do not paste them
with unresolved placeholders. Wrangler manages its own authentication; never
extract credentials. Check the account, database and Worker before each remote
operation. Export blocks database requests, so keep writers paused. Protect the
SQL file with owner-only access, encrypt with an existing approved tool, verify
its checksum, store outside the provider with an independently held key and verify
decryption. Never put dumps or holdings in release assets/public logs.

Time Travel on D1 Free covers seven days and is not independent backup. A bookmark
is not proof of unchanged data. Retain baseline counts plus privately computed
ordered digests of financial rows, canonical JSON, approvals/receipts and anchors;
compare byte-exact decimals/JSON, not floating-point totals. No such data enters docs.

## 2. Rehearse adoption and recovery on the private copy

Use an already approved isolated target with no production binding or scheduler.
The synthetic fixtures do not authorize loading actual data into a new target.
A real-snapshot rehearsal requires explicit approval for that private environment.
Decrypt/import the export, verify counts/digests and financial projections against
the frozen baseline. A source export is not a tested recovery until this succeeds.

Rehearse 0008 then 0009 on the restored copy using the existing source migrations,
without modification. Export/import preserves decimal TEXT and canonical payloads;
verify this explicitly, including migration history and trigger behavior. D1's SQL
import limitations and immutable triggers can make ordering significant: stop on
failure, do not disable guards or hand-edit financial rows to make a restore pass.

0008 adds `portfolios` and deterministically adopts operational references first,
then historical journal anchors. It retains the same portfolio UUID, owner,
opening UUID/revision and kind. Existing rows are active with a generic historical
name; it creates no replacement transaction or invented starting balance. Conflicting
or unresolved anchors must abort. 0009 extends anchor validation and adds the
active-owner-kind write guard; it does not rewrite historical events or receipts.

Verify privately:

- The existing real portfolio resolves exactly once; its operational/historical
  anchor agrees with the configured binding and its journal.
- Old opening/operational reference, instrument catalogue, event sequence, journal
  version, balances, approvals, receipt JSON and digests match the baseline.
- Existing real holdings/cash/cost projections remain identical. Preserve the
  configured performance reference; no re-import or recalculation of source values.
- Other owners are excluded; future simulated portfolios have independent UUIDs,
  openings and journals, and reuse shared quotations without copying real holdings.
  There is no public portfolio-administration tool; do not create a fake entry in
  the real PEA to test isolation. Existing synthetic evidence covers these cases.

## 3. Apply only the two pending migrations

Keep old code and all writers quiescent. Review the pending list: **only 0008 and
0009** are expected. Then, under delivery approval:

```sh
node node_modules/wrangler/bin/wrangler.js d1 migrations apply '<EXISTING_DB>' --remote --config '<DB_CONFIG>'
node node_modules/wrangler/bin/wrangler.js d1 migrations list '<EXISTING_DB>' --remote --config '<DB_CONFIG>'
```

Wrangler applies pending migrations in order; this is not one transaction spanning
both. A failed migration rolls itself back; a previous successful migration remains.
If 0009 fails after 0008, stop with writers paused, inspect actual state privately and
use the approved recovery path. Do not blindly reapply, edit d1_migrations or drop
the registry. Confirm both migrations and repeat the private baseline comparisons.
No code requiring the registry is deployed before the schema/adoption gate passes.

## 5. Read-only hosted acceptance

Refresh/reconnect the ChatGPT connector catalogue once after deploying new tools.
Avoid repeating reconnections as a diagnosis. Capture only sanitized results:

1. Technical `ping({})` succeeds; anonymous MCP/V2 reads are refused by Access or
   the application. A login redirect is not evidence that the application ran.
2. `list_portfolios` is registered once, returns only the owner registry and gives
   `data[].id`, never opening identifiers. Its common envelope remains compatible;
   V2 entries intentionally contain richer metadata than the V1.1.5 singleton.
3. Read the existing real portfolio through V1.1 current/journal tools and V2
   details/state/valuation; compare the same stored quotation selectors, timestamps
   and baseline financial values. No provider fetch is requested. Missing/stale
   quotes remain explicit; do not require a misleading fresh-price success.
4. Read-only REST/MCP paths agree. Invalid/opening UUIDs and unauthorized identities
   disclose no other portfolio. Wrong AUD/browser service credentials stay refused.
   With writes disabled, approval refusal alone does not prove browser-AUD checking.
   If delivery approval covers it, temporarily enable the existing identity-only
   FINANCIAL_APPROVAL_DIAGNOSTICS_ENABLED flag (writes must remain false) and check
   `/financial-confirmation/auth-check` on the approval origin: valid browser identity
   succeeds; wrong AUD/service/Bearer credentials fail. Disable diagnostics afterward.
   This grants no financial approval and creates no proposal.
   Use existing authorized synthetic/security fixtures where a second real identity
   is unavailable; mark any hosted negative case still unverified.
5. Check sanitized auth/error diagnostics, latency and D1 row usage; no journal
   append or approval write is part of this acceptance. Never exercise a preparation,
   confirmation, real purchase or fake transaction on the real PEA.

Only after these gates and the delivery authorization explicitly covers it, restore
the prior approved financial-write setting and resume existing ingestion/scheduling.
This is a configuration action, not a financial operation. Do not claim production
replay/concurrency/failure acceptance from read-only checks. A first V2 financial
write requires a separate exact owner intent; no test write is required for this step.
Observe normal authorized collection/closing monitoring without a new campaign.

## 6. Capacity, retention and operating cost gate

Keep Yahoo principal, EODHD observation only, cadence 30 minutes, shared-session
experiment inactive. The earlier samples/counters remain historical evidence,
not current account budgets or permission for another fetch.

[Published D1 limits](https://developers.cloudflare.com/d1/platform/limits/) distinguish
500 MB per Free database from 5 GB per Free account; query limits are 50 per Free
Worker invocation. Check the deployed account/plan and headroom, not just SQLite
file size. [Pricing](https://developers.cloudflare.com/d1/platform/pricing/) defines
5 million rows read/100,000 written per Free day, reset UTC; indexes add billed writes.
No paid plan or automatic credit use is authorized if a limit is reached.

E's synthetic sizing measured 1,576,960 extra bytes for 26 cycles/520 observations,
versus 3,158,016 for 52 cycles. At 252 such days, the 30-minute case alone projects
about 397 MB; this is arithmetic over a synthetic sample, not a capacity guarantee
or measured bill. Include existing tables/indexes, financial history, partial failures,
receipts and backups. Measure actual D1 rows and Worker execution before acceptance;
local observation counts cannot be treated as billed writes. Standard Actions runners
are free for this public repository, but latency/queueing/retention remain constraints.

The existing [INSTALL retention/recovery policy](../INSTALL.md#delivery-stages-and-remaining-gates)
proposes at least 12 months of quotations, daily encrypted independent exports,
30 daily backups and tested recovery. Destination/key and recovery proof are open.
Quotation/event triggers enforce immutability; no DELETE-based purge/rotation is
implemented or authorized. If remaining headroom cannot satisfy the agreed horizon,
stop and obtain an explicit retention/storage decision before rollout. Do not remove
immutability, silently shorten retention, or purchase storage as part of this task.

## 7. Rollback: code and data are different decisions

**Code failure, data intact:** keep writers paused, route the existing Worker back
to the recorded V1.1.5 version using the official dashboard or reviewed
`wrangler rollback '<PREVIOUS_VERSION_ID>' --config '<FINANCIAL_CONFIG>'`.
Worker rollback does not revert D1, Access policies, OAuth, ingestion or scheduler.
Leave additive registry rows/migrations in place; do not drop tables or decrement
migration history. Confirm the old configured real binding still resolves and read
results match; stop if newer writes/anchors make that assumption false.

**Data corruption/adoption failure:** do not use code rollback as a data repair.
Freeze every writer, capture the damaged state for private diagnosis, select the
verified bookmark or independent backup, and obtain the specific destructive
restore approval. Time Travel overwrites the whole database, including quotes,
receipts, approvals and all portfolios; it can lose newer valid transactions.
Reconcile the loss window explicitly, revoke/expire stale proposals and account
for receipts that may otherwise be replayed after restore. Never reconstruct lost
real financial events without exact owner intent and duplicate checks.

Future approved in-place recovery template:

```sh
node node_modules/wrangler/bin/wrangler.js d1 time-travel restore '<EXISTING_DB>' --bookmark '<VERIFIED_BOOKMARK>' --config '<DB_CONFIG>'
```

Independent SQL recovery must first succeed on an authorized isolated empty target;
never import a full export over populated production tables as an improvised restore.
Restore/import ordering and triggers must have been rehearsed. Reapply required
deletion manifests before serving data. OAuth/Access configuration needs its separate
recorded recovery procedure. Recheck schema, anchors, receipts and read projections
before resuming. No destructive restore is authorized by this preparation.

## 8. Publication sequence and release record

After explicit delivery authorization: approved main merge → frozen-writer backup
and isolated recovery/adoption proof → 0008 → 0009 → schema/baseline checks →
reviewed Worker deployment with writes paused → read-only hosted acceptance →
authorized restoration of existing service flags/scheduling → monitored acceptance
record → annotated `v2.0.0` at the exact accepted main revision → GitHub release
using [draft English notes](v2.0.0.md). Do not tag the old integration test SHA as
if it were the eventual deployed main merge. Verify the final source/license diff;
application changes require affected checks, docs/license-only changes reuse evidence.

The release record must state exact SHA, migration IDs, Worker version, actual
acceptance outcomes and retained limits. Publish source only, no private export,
configuration, capture, journal, wheel, node_modules or image. GitHub-generated
archives may be used after authorization. The package/diagnostic version remains
0.1.0 today; a Git release number is a separate identifier, not proof of deployment.
Do not silently rewrite runtime/package versions or tag as part of this preparation.
