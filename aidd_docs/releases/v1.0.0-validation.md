## Current architecture

Protected financial read REST/MCP and quotation ingestion use separate Cloudflare Workers and Access policies. Read-only MCP and REST adapters share application/domain services and D1 repositories. Python/yfinance supplies observations, never writes D1 directly and never computes portfolio results.

`src/entrypoints/scheduler.ts` and `src/scheduling/github-dispatch.ts` compose Cloudflare Cron → durable per-slot claim → GitHub `workflow_dispatch` → existing protected collector/monitor jobs. The scheduler has no financial binding, ingestion credential or public HTTP endpoint. A dispatch acceptance is not proof of a successful collection. Ambiguous dispatches are not retried automatically; receipts are not deleted to force replays.

Collection: weekdays 07:17–19:47 Europe/Paris, default 30 minutes, 26 slots. UTC crons are `17,47 * * * *` and `9 * * * *`; Paris filtering handles winter/summer time without a holiday-calendar claim. Closing candidate extends monitoring from 07:09–19:09 to 07:09–20:09: 14 monitor dispatches, hence 40 total weekday dispatches at default cadence. The 20:09 pass requires every due slot in the final covered collection hour, not merely any recent successful run; for slower cadence it finds the last hour with a due slot.

## Changes and known limits

- `cd055e9`: normalize Cloudflare scheduled timestamps to a canonical minute; provider timestamps may contain seconds/milliseconds. Keep future/late rejection and one durable claim per slot.
- `d5e8fe3`: remove the arbitrary total assertion-lifetime cap. RS256, trusted JWKS, issuer, exact audience, type, allowlisted signed machine identity, iat/exp/nbf, clock tolerance and ingestion grants remain enforced. Python sends service headers; Access issues the JWT. Observed 401 alone did not prove the excessive-lifetime predicate. Existing issued assertions can remain valid until expiry; no instant-revocation guarantee.
- Current scheduler production version before closure: `9232bf50-904e-4594-bbc7-209e9080495f`; ingestion fix: `6a4b1ec7-f888-4328-b1f6-1572405ecbf9`. Record the closure scheduler version only after deployment.
- Native GitHub schedules were irregular even in a minimal diagnostic; stop repeating schedule-registration experiments. Keep workflow_dispatch, pinned Actions, repository/main gates, collector-live, approval flags, concurrency, Access and idempotence.
- The old minute-shift experiments were discarded locally; they are not part of the closure. Historical `ops/cloudflare-scheduler` templates/patch are preparation evidence, not current deployment sources or rollback commands.
- Ordinary monitoring tolerates gaps up to the configured recent-success threshold. Closing monitoring is explicitly stricter. Independent alert delivery, backup/restore drills, calendar/freshness and comprehensive transaction/performance accounting are not claimed as completed.
