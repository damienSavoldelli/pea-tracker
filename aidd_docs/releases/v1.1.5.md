## Incident and correction

ChatGPT supplied `opening_state.id` to `get_current_portfolio` as `portfolio_id`.
These identify different objects. The existing owner/portfolio binding correctly
returned `portfolio_access_denied`; successful historical reads did not contradict
that refusal because those tools need no portfolio UUID. The interface had no
autonomous discovery path: current reads and the journal already required the ID.

- Add read-only MCP `list_portfolios`, available with `portfolio:read`, without
  requiring financial write permission. Its application service enforces the same
  configured owner and portfolio binding and real-portfolio guard as journal reads.
- Return only the configured V1.1 portfolio, using existing read-only journal
  resolution. No registry, migration, dependency change, new environment setting,
  financial write, proposal or approval is introduced.
- Current state/valuation, journal and six preparation tool descriptions direct
  the agent to `list_portfolios` → `data[].id`. The opening-state tool also explains
  that its ID is an opening revision. Never use `opening_state.id` as `portfolio_id`.
- Historical V1 data contracts, exact financial rules, access-denial behavior and
  V1.1.4 independent browser approval/audience/Origin protections are preserved.
  The fully enabled catalogue becomes 19 tools: 12 reads/diagnostics, six
  preparations and one confirmation, compared with 18 in V1.1.4.

## Contract and V2.0B compatibility

Reuse the existing V2.0B name and strict query: optional `limit` (integer 1–100,
default 50) and `after` (UUID, exclusive ascending ID boundary). Unknown query keys
are refused. V1.1 has at most one entry, so every page has `next_after: null`.

Synthetic response:

```json
{
  "data": [{ "id": "10000000-0000-4000-8000-000000000001", "kind": "real", "status": "active" }],
  "page": { "next_after": null },
  "read_only": true
}
```

`read_only` describes this listing; it grants no financial permission. `active`
describes the configured V1.1 portfolio, which has no archive lifecycle. Discovery
fails closed if its existing journal/opening cannot be resolved or is not real.

This is a **metadata subset**, not the complete V2.0B registry response. V1.1 has
no registry name, metadata version, lifecycle timestamps or registry opening-source
record; these are omitted rather than fabricated. V2.0B can enrich entries without
changing `data[].id`, `kind`, `status`, the query or the pagination envelope.

Future integration must replace this singleton registration/service with the
registry-backed `registerPortfolioReadTools`/`PortfolioReadService.list`, not mount
both `list_portfolios` registrations. Keep one query schema and one registration;
retain the discovery guidance in the legacy tool descriptions. Do not route every
listed V2 portfolio to legacy `get_current_portfolio`: that tool stays bound to
the configured V1 portfolio; V2 uses `get_portfolio_state` for selected portfolios.
No V2 worktree is changed by this backport.

## RETEX — interfaces for agents

An MCP tool must be secure and technically correct **and** let an agent discover
every required parameter from an authorized tool result, without human input or
guessing. A response that only returns an ID after requiring that ID is not a
discovery path. Unlike a REST integration with a configured client, an autonomous
agent needs an explicit entry tool and semantic guidance distinguishing entity IDs
from snapshot/revision IDs. Acceptance should start without a known portfolio ID,
follow discovery to the dependent read, and check that the wrong ID remains denied.

The owner approved this learning in the incident discussion. It is also retained
in [coding assertions](../memory/coding-assertions.md); existing production limits
remain in the [V1.1 validation record](v1.1.0-validation.md).
